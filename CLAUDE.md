# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

WhatTheFlight is a SwiftUI-based flight tracking application that monitors aircraft overhead using FlightRadar24 API data. The project targets iOS, macOS, and visionOS platforms and displays real-time flight information within configurable geographic bounds.

## Build & Test Commands

This is an Xcode project using standard Xcode build commands:

- **Build**: `xcodebuild -project WhatTheFlight.xcodeproj -scheme WhatTheFlight -configuration Debug build`
- **Test**: `xcodebuild -project WhatTheFlight.xcodeproj -scheme WhatTheFlight -configuration Debug test`
- **Run Tests**: `xcodebuild test -project WhatTheFlight.xcodeproj -scheme WhatTheFlight -destination 'platform=iOS Simulator,name=iPhone 15'`
- **Clean**: `xcodebuild -project WhatTheFlight.xcodeproj -scheme WhatTheFlight clean`

For development, open `WhatTheFlight.xcodeproj` in Xcode.

## iOS / iPadOS app (radar v2) — start here

iOS runs the redesigned radar (`RadarRootView`) and tvOS `TVRadarRootView`, selected in `WhatTheFlightApp.swift`; watchOS is its own app. Only macOS still runs the legacy `ContentView` stack described under "Architecture" below. It lives in `WhatTheFlight/Legacy/` (tests in `WhatTheFlightTests/Legacy/` and `WhatTheFlightUITests/Legacy/`), every file wrapped in `#if os(macOS) || os(visionOS)`, so none of it is compiled into the iPhone, iPad or TV apps. Don't build on it; it goes once the Mac runs the iPad app (Enhancements C11). visionOS doesn't build (the legacy `LocationManager` uses APIs it lacks).

Layout (all under `WhatTheFlight/WhatTheFlight/`):
- `Core/` — platform-neutral, unit-tested logic: `GeoMath` (distance, bearing, dead reckoning, closest approach, elevation above the horizon), `Flight` / `RadarContact` (`RadarContact.altitudeFeet` is dead-reckoned from the vertical rate like the position, capped at 90 s: show and say it rather than `flight.altitudeFeet`; `RadarContact.profile` is a `FlightProfile`: operator, notable tags, type, silhouette, airline, built once per flight per feed by `RadarModel`; per-tick code and views read it rather than the `Flight` computed properties), `Log` (one `os.Logger` per area: feed, logbook, sync, link, sensors, camera, alerts, ui; use it instead of `print`), `PollingPolicy` (the poll interval, which has no setting: 5 s within a mile of the nearest aircraft (now or within 90 s), then 5 s + 1 s per mile up to 25 s, 30 s when the feed reports nothing; Low Power Mode × 1.5 with a 10 s floor; `RadarModel.pollsFastest`, set by Sky View and the Watch's Identify / Find, holds it at the floor; Watch floor 10 s), `FlightFeedParser` (FR24 `feed.js` array format), `PerimeterTrack` (rounded-rect edge path + optimal icon spacing; its 1,440 samples are cached by rect, so layouts can rebuild it freely), `FocusPolicy` (which aircraft owns the centre), `OperatorInfo` (the line under the flight number: airline, "Private aircraft · 🇺🇸 United States", "Unlisted operator XYZ"), `NotableTraffic` (emergency squawks, military, government, air ambulance, rare types), `RouteProgress` (miles flown / to go), `SkyProjector` (pinhole camera maths for Sky View: project / unproject, `reframed` for a photo or video frame), `CameraZoom` (Sky View lens maths: field of view per zoom factor, 0.5× / 1× / 2× / 5× stops), `SkyCorrection` (Sky View visual lock-on: `SkyBlobDetector` finds the aircraft as a dot near its predicted spot, `VisualFix`, and the learned compass yaw applied to every label), `Whereabouts` ("Where is it now?" wording: in the air / on the ground at ATL, still on vs now flying, distance from you), `WristPointing` (Apple Watch Point & Find: forearm direction from attitude + wrist/crown settings, guidance, haptic cadence).
- `Data/` — offline catalogs: airlines (ICAO + radio callsign), aircraft types + helicopter detection + radar silhouettes (`AircraftTypeCatalog.silhouetteCodes` → `AircraftSilhouette`; unknown codes get the airliner), airports (IATA → city/name/coordinates), `RegistrationCountry` (tail-number prefix → country). `AirlineCatalog+Data.swift` (~5,800 rows, OpenFlights, ODbL) and `AirportCatalog+Data.swift` (~8,800 rows, OurAirports, public domain) are GENERATED by `Scripts/generate_catalogs.py`; the hand-curated lists in `AirlineCatalog.swift` / `AirportCatalog.swift` override them, so fix names there. `Catalogs.warmUp()` parses them off the main thread at launch (app inits, widget / complication / Top Shelf providers). Callsign lookup order: feed airline field → special words (`SAM`, `LIFE`, `NAVY`…) → 3-letter ICAO prefix followed by a digit.
- `Radar/RadarModel.swift` — `@Observable` state machine: polling with backoff, 1 Hz dead-reckoning tick, radius filter, focus, queued notices, per-flight trails (feed positions seen while watching, for the map). Trails are kept only out to 1.5× the radius (or the TV map's ring, `trailRadiusFloor`) plus focused and pinned aircraft. It also feeds `logbook?.record(...)` (`isLogging`: live traffic only — never demo, never an iPhone custom spot; the TV sets `logsCustomSpot` because its set place is its real location) and runs `TrafficAlertEngine`; alerts go to `onAlert` or become notices. The observer coordinate is pushed in, so it has no CoreLocation manager dependency.
- Pinning & worldwide search: one "pin" concept everywhere (hold the hero, TV ⏯ / dock, detail screens, search rows). Pins are `PinnedAircraft` (in `Core/FocusPolicy.swift`; matched by registration, else callsign, so they follow an airframe onto its next leg), stored in `RadarSettings.pinnedAircraft` (`wtf.pinnedAircraft`, JSON, max `RadarModel.maxPins` = 5; the oldest makes way with a notice). `RadarModel` looks up pins the main feed's box missed with `FlightFeed.lookup` every ~20 s (`pinnedFlights`, dead-reckoned between), so they appear in `outsideContacts` however far away; `pinnedOutside` / `perimeterContacts` put them on the radar edge, `pinnedIDs` feeds `PerimeterLayer` / `TrafficMap` (a pinned aircraft's mile label on the radar edge is yellow, `Palette.pinned`, the same yellow as the pin by the flight number on the hero; never faded; the map draws no pin mark). `focus.isPinned` is always derived (every focus change goes through `setFocus`). `focus(on:)` pins an aircraft outside the radius (search, logbook "Show on Radar", detail screens, deep links, the TV's lists); map taps and radar-edge taps pass `pinning: false`, so an aircraft picked on the map outside the radius is only held (`RadarFocus.isHeld`): it keeps the centre and rides the radar edge while it's within the map's fringe (`RadarModel.fringeMiles`, 1.5× the radius), then the nearest takes over ("… flew out of range"); flying into the radius makes it an ordinary focus, pinning it drops the hold. `RadarModel.searchAnywhere` → `FlightRadarFeed.search`: three parallel world `feed.js` requests (`reg=`, `flight=`, `callsign=`; FR24 filters are uppercase prefix matches, take comma lists and AND together; registrations only match with their hyphen, so `RegistrationCountry.hyphenatedForms` adds `G-XLEI` for `GXLEI`). UI: iPhone `FlightSearchSheet`, TV `TVAircraftListView` (dock → Aircraft, now `.searchable`). The map follows a far-away pinned focus on its own (`TrafficMapGeometry.followsPinnedAlone`). Pins sync across iPhone, iPad, Apple TV and Apple Watch through iCloud key-value storage (`Services/PinSync.swift`, always on, independent of the logbook switch): one key per pin (`pin.<registration|callsign|flightID>`, JSON), `wtf.pinsInCloud` remembers which ids this device has seen in iCloud so a missing key means "unpinned elsewhere" vs "not sent yet"; demo pins never sync; `pinnedAt` orders pins and the cap across devices. All three apps' entitlements set `com.apple.developer.ubiquity-kvstore-identifier` to `$(TeamIdentifierPrefix)SargeyWargey.WhatTheFlight` so they share one store; `RadarModel.pinsDidChangeElsewhere` reacts to remote changes. DEBUG: `-wtf.debugPin <query>` pins the first worldwide hit, `-wtf.debugAircraftSearch <query>` pre-fills either search screen.
- `Radar/SpotPhoto.swift` — Sky View photos: `SpotPhoto` (the aircraft and its stats at the shutter, where it sits in the frame) rides on `Sighting.photos` (merged as a union minus `removedPhotoIDs`); `SpotPhotoStore` keeps the logbook's 1600 px HEIC copy per photo in Application Support/SpotPhotos. Photographing an aircraft outside the radius still logs it (`Logbook.addPhoto`). The full-resolution original goes to the camera roll (add-only, no album, flight in IPTC caption/keywords; setting `wtf.skySaveToPhotos`).
- `Radar/Logbook.swift` — sightings persisted as JSON in Application Support (a file that won't decode is set aside as `Logbook-unreadable-<time>.json`, never saved over), `LogbookStats`, `DailyRecap` ("Today's highlights": notable aircraft, first-of-type, new airlines). `Radar/LogbookDigest.swift`: `LogbookDigest`, everything the logbook screens show, built in one pass (today, records, `LogbookDay` / `LogbookMonth`, `LogbookRanking` lists of aircraft seen more than once / airlines / types / routes / airports / countries, places, the sky charts, streaks, the busiest hour, first-of-type ids) and `LogbookFilter` (quick filters and a ranked entry's sightings). Views read `Logbook.digest`, cached per change and per day; past `Logbook.backgroundDigestThreshold` (2,000) sightings a change rebuilds it off the main thread while screens keep the old one. Per-sighting calendar maths goes through `DayClock` (Calendar calls are slow over 10,000 sightings). `Radar/LogbookSky.swift`: the place-dependent charts (hour, weekday, heading rose, altitude) are a `LogbookSky`, built for everywhere (`digest.sky`) and for each `LogbookSpot` (`digest.spots`: sightings grouped by observer coordinate, ~7 mi grid squares busiest first joining the nearest spot within 15 mi, named after their most common `placeName`; sightings without a position join the spot with their place name). A chart only shows once `LogbookSky.minimum` (50) aircraft back it (`showsTimes` / `showsHeadings` / `showsAltitudes`), else a "filling in" progress bar (`LogbookSkyProgress`). Hours and weekdays use each sighting's own `timeZone` (recorded at logging; older ones borrow their spot's usual zone). The Stats tab (iPhone, iPad, TV) is two halves: "Your sky" (one spot, picked by `digest.sky(_:near:)`: where you are once its charts are ready, else the spot with the most sightings; a menu on iPhone / iPad, chips on the TV, plus "All places") and "Everywhere" (summary, activity, records, rankings, places). `Radar/LogbookAchievements.swift`: `Achievement` badges, derived from the sightings every time (nothing stored), 46 in five `Achievement.Group`s (Milestones, Rare Birds, Moments, Collections, Sky View); most have `tiers` (Plane Spotter 100 / 1,000 / 10,000 / 100,000 / 1,000,000) with `level`, `target` = the next level, and top levels are meant to need calendar time, travel or luck, not just a radar left running (Busy Sky only counts aircraft within 5 mi, so the radius doesn't help). A badge whose levels aren't plain counts sets `tierLabels` ("45,000 ft", "¼ mi") and `progressLabel`; best-ever ones (High Flier, Speed Demon, Right Overhead, Long Haul, Far From Home) set `isRecord`, so the ring shows levels earned and they're never "next up". Show progress with `progressText` / `targetLabel`, not `progress` / `target`. A maxed levelled badge gets a filled disc and an outer ring (`AchievementBadge`). `Logbook.onBadgeUnlocked` (wired to a radar notice on iPhone and TV) fires for new badges and levels, checked at most every 20 s when new sightings arrive; levels already announced are kept in `wtf.announcedBadges` by what they take (`spotter@1000`, so a changed ladder never skips or repeats one), and the first check on an existing logbook only records a baseline. Fence Spotter looks up airports with `AirportCatalog.nearest` (grid-indexed by degree); Six Continents uses `Airport.continent`. `LogbookDigest`, `LogbookSky` and `LogbookAchievements` are in the Watch target's membership list. Each `Sighting` records `devices` (`LogDevice`) and `placeName` (reverse-geocoded by `Services/PlaceNamer`, set on `RadarModel.logPlaceName`). `Services/LogbookSync` merges logbooks across iPhone / iPad / Apple TV with CloudKit `CKSyncEngine` (container `iCloud.SargeyWargey.WhatTheFlight`, zone `Logbook`, one record per flight id holding the sighting as JSON; copies merge via `Sighting.merged(with:)`; each photo's image is its own `SpotPhoto` record "photo-<id>" with a CKAsset, and `LogbookSync.downloadPhoto` fetches one on demand). Setting `wtf.iCloudLogbook`. Custom spots and demo traffic are never logged on iPhone (`RadarModel.isLogging`); the radar shows a "Custom spot · … · not logged" tag along the bottom. Demo traffic turns the bar's aircraft count into a solid ink "DEMO n" lozenge (`StatusBadge(highlightsDemo:)`, the TV keeps the glass badge) and adds a "Demo traffic · simulated aircraft · not logged" tag (`DemoTrafficTag`; tap → "Switch to Live Traffic"). Both tags sit just above the bar. `Radar/TrafficAlerts.swift` — overhead (closest approach within N mi in ≤150 s) and notable alerts, once per flight per reason.

- `UI/` — SwiftUI views. Text in sheets, lists and pages uses `.monoScaled(size, weight)` (Dynamic Type) and `radarCaption(scales: true)`; `Font.mono` is fixed, for the radar face, the Watch radar, the TV and the shareable card. A view that owns a reference type holds it in `@LazyState` (`UI/LazyState.swift`), not `@State private var x = Object()`, which builds a new object on every view init (sheets over the radar are re-created every tick and compass update). `RadarScreen` composes `RadarBackdrop`/`CompassBezel`, `FlightHero`, `PerimeterLayer` and `RadarControlBar`, a floating glass capsule along the bottom (iPhone and iPad): Map / Radar (named for where it goes; only with Map view on and no map pane beside the radar), Sky View (`SkyRequest()`, so lowering the phone doesn't close it), a divider, the live dot + aircraft count captioned "Aircraft" (search sheet at full height), Logbook and Settings. `RadarChrome` places the bar like a tab bar (22 pt off the screen's bottom edge with a home indicator, 10 pt without; scaled down if a narrow window can't fit it) and the tags above it; the radar face (`RadarLayout`, bezel and icon track) is laid out only in the room above, so nothing on the edge needs avoiding. On the iPhone Duo in landscape its buttons move to the system's vertical bar strip instead, Safari-style (see iPhone Duo below). - Topography (the contours behind the radar, iOS + tvOS): generated, not an image. `UI/TopographyShader.swift` holds Metal source compiled at runtime (`makeLibrary(source:)`), so the build doesn't need Xcode's separately downloaded Metal Toolchain; don't add `.metal` files. `UI/TopographyRenderer.swift`: a compute pass builds a height field (simplex fBm, seed 1, hills `featurePoints` = 600 pt on TV, 420 iPad, 340 iPhone) once per style and size into an r32Float texture shared by every screen; a fragment pass draws one anti-aliased line per elevation (every fifth heavier) on `Palette.paper`. Styles `RadarSettings.TopographyStyle` (`wtf.topography`: off, remaster, survey (default), highlands, relief; per-style numbers in `TopographyRenderer.Look`). Motion is Tide only: `TopographyMotion` (`wtf.topographyMotion`: off, half, normal (default), double) shifts which heights get a line, 0.05 levels/s at 1×, on the main radar only (`RadarBackdrop(topographyMotion:)` → `TopographyMetalView`, an MTKView at 20–30 fps, paused when inactive or in Low Power Mode, still with Reduce Motion). Every other backdrop gets a cached still image. The style reaches backdrops through `\.topographyStyle`, injected at both roots and into their presentations; `showTopography` is now derived (`topography != .off`), and an old `wtf.showTopography = NO` migrates to Off. The tour's miniatures pass `topographyZoom`. Settings: iPhone/iPad Display → Topography (`TopographySettingsPage`, previews), TV Display pane chip rows. - iPhone Duo (the folding iPhone, iOS 27.1+; simulator "iPhone Duo"): a 466 × 678 pt cover screen and a 951 × 669 pt inner screen with a fold down the middle. `Services/FoldMonitor.swift` reads the hinge (`UIHingeInteraction`: closed / partially open / fully open) and the fold strip (`UIView.reservedRegions(kind: .division, options: .includeInactive)`: the crease plus a 20 pt margin each side, x 455.5–495.5 held as a book), and settles them into `FoldPosture` (`Core/FoldLayout.swift`, unit-tested: none / flat / book / tabletop; half-open postures only count after 0.35 s, so unfolding straight to flat doesn't flash the split). Half open with Map view on, `RadarRootView` gives each side of the fold half the screen: book (fold top to bottom) radar on the left page, `TrafficMap` on the right; tabletop (fold across) radar on the standing half, map on the half lying on the table. The halves end at the strip, which `FoldGutter` fills, so nothing tappable sits on the crease. Panes are placed by frame (`PaneLayout`, in `RadarRootView`), in window coordinates because the strip is, so the radar keeps its identity through flat ↔ book ↔ tabletop. Flat or folded shut, one view at a time (the bar's Map button). Short radar panes get the one-row stats (`RadarLayout.prefersWideStats`) and below 420 pt a compact hero without the type line and approach chip (`prefersCompactHero`); the hero also shrinks to fit (`heroScale(fitting:room:)`). iOS doesn't ask the app for orientations on the inner screen: it turns with the phone like an iPad's. The cover screen turns too, all but upside down (`RadarAppDelegate` allows it once `FoldMonitor.phoneFolds`; other iPhones stay portrait), and `RadarLocationService.interfaceOrientations` (from `FoldMonitor.interfaceOrientations`) makes the compass follow the device on both. In landscape (either screen) the Duo uses iOS 27.1's vertical bar: the status bar stands on end at the top of a strip down the trailing edge (inner screen: the safe area's 84 pt right inset; the status bar is the active `.occlusion` reserved region at its top, 84 × 120 pt), and `UITraitCollection.verticalBarEdge` says which side. `FoldMonitor.verticalBar` reads both, and while it's set `RadarRootView.controlRail` puts `RadarControlBar(rail:)` in the strip, laid out like the system's own bar there (Safari's): Map / Radar and Sky View as round glass buttons from just under the status bar, the aircraft count, Logbook and Settings grouped in a glass capsule at the bottom, symbols without captions (the count stacks the live dot over the number). `RadarControlBar.Rail` sizes it from the strip's width as the system does: a seventh to the content, four sevenths of button, two sevenths to the screen's edge (inner screen: 48 pt buttons in the 84 pt strip, first one at y 120, 10 pt apart, the group ending 27 pt off the bottom, all matching the system). It sits at the screen's far edge even with the book posture's map pane beside the radar. `RadarScreen(showsBar: false)` then drops its bottom bar, so the radar takes the full height and the tags sit where the bar was. `RadarMapPane` adds the trailing safe inset to its card inset, so the recentre button and ring stay out of the strip. The inner screen also reports its interface orientation a quarter turn round from the phone's body (held as a book: device portrait, interface landscapeLeft), so Sky View maps Core Motion with `UIWindowScene.bodyInterfaceOrientation`. Raise-to-look is off while half open. Settings → Display's Map footer explains the fold when `\.isFoldable`. The simulator's hinge and pose are only movable from DeviceHub's device window (`devicectl device orientation set` doesn't stick on the Duo, and `devicectl device motion hinge-angle` only reads it); DEBUG `-wtf.debugFold book|tabletop|flat` forces a posture.
- `UI/TrafficMap.swift` — the shared ambient map (iOS + tvOS): every in-range aircraft (`AircraftBlip`, glyph only: no callsign or altitude on the map, the radar / hero card names the focus), fringe traffic up to 1.5× the radius at 40 %, the focused aircraft wherever it is, trails faded by age (`TrafficMapGeometry.segments`, rebuilt on `RadarModel.trailVersion`, i.e. per feed, not per tick), airport pins only for origins/destinations of drawn flights, the radius ring with half/quarter echoes, and a paper wash polygon over the base map (`.muted` alone barely mutes it). The camera fits the ring once and only moves for radius / place / "up" changes or to keep a pinned aircraft that left the radius in view. A turned map needs a `MapCamera` distance, which it learns from MapKit's first region fit (`metresPerMile`). It also holds the pieces `DetailMap` shares (`RadiusRings`, `ProjectedPath`, `ObserverDot`, `AirportPin`); the maths is in `Core/TrafficMapGeometry.swift` (unit-tested).

Behaviour rules (from `Working Spec.md`): the nearest aircraft takes the centre and stays there until it leaves the radius or the user swipes right; icons sit on the screen edge at their compass bearing (rotating with the phone), face their real track, never under the Dynamic Island / home indicator, with whole-mile labels between icon and centre.

### Apple TV (radar v2)
tvOS runs `TVRadarRootView` (`UI/TV/`), reusing the same model, core and visual components (`FlightHero`, `PerimeterLayer`, `RadarBackdrop` take a `scale` for the 10-foot view). "Up" on the TV is `RadarSettings.tvFacingDegrees` — the compass direction the viewer faces when watching. Remote: ◀/▶ closer/farther aircraft, ▲ = next view (Radar → Split → Map, with Map view on), click = details, play/pause = pin, ▼ = dock (Nearest, Pin, Aircraft, Settings); hints sit in a footer in the bottom overscan margin and the dock only appears after ▼. Place search is a full-screen `.searchable` with `PlaceCompleter` (MapKit `MKLocalSearchCompleter`) suggestions as you type. `TVRadarSettingsView` is a sidebar + chip-row design (tvOS has no sliders), panes in the order Radar, Display, Location, About (`TVSettingsPane`; the dock's Settings opens Radar, setup flows open Location); location can come from the iPhone, MapKit place search, the Apple TV's own Wi-Fi location, or typed coordinates. The TV has no "Show helicopters" switch: `RadarSettings` forces `showHelicopters` on under tvOS.

iPhone → TV link (`Services/TVLink.swift`): MultipeerConnectivity, service `wtf-radar`. The TV advertises a 4-digit code and auto-accepts; the iPhone (`UI/TVLinkSetupView.swift`, Settings → Apple TV) sends `TVLink.Payload` (lat/lon + facing) and waits for an `Ack`. Facing comes from `AimingCompass` (Core Motion attitude vs true north: back-camera direction when upright, top edge when flat). Bonjour/local-network/camera keys live in `Config/WhatTheFlight-Info.plist`, merged via `INFOPLIST_FILE`.

Ambient map (TV): with Map view on (`wtf.mapView`, default on; Settings → Display) the TV has three views in `wtf.tvView` (`RadarSettings.TVView`: `radar`, `split`, `map`, remembered; read it as `settings.effectiveTVView`, which is the radar whenever Map view is off). Settings → Display → View picks one, and ▲ on the hero or the dock's view item steps through them (`TVView.next`, `TVRadarScreen.showNextView`: Radar → Split → Map → Radar; the button is named for the view it switches to). Split: `TVRadarScreen` narrows the radar face to the left 60 % of the screen (`splitRadarShare`, overscan included) and puts `TVTrafficMap` beside it; the hero widens to 80 % of the pane and the dock shrinks to fit it (laid out at its natural width, then scaled). Map: `UI/TV/TVMapStack.swift` is the layer `TVRadarScreen` swaps in for the radar face: full-screen `TVTrafficMap` (a `TrafficMap` turned to the TV's facing, or north up, `wtf.mapNorthUp`) plus the hero card bottom-right. The badge, hints, dock and every remote command stay in `TVRadarScreen` (`heroButton` is the focus anchor on every view; the map is disabled and never focusable). On the full-screen map, after 30 s without input the badge and hints fade (ambient settle); the first time Split or Map opens with Keep screen awake off it posts a one-off notice (`wtf.mapAwakeHintShown`). The TV map has its own range, `wtf.mapRadius` (`mapRadiusMiles`, nil = the radar's; read `effectiveMapRadius`): `TVTrafficMap` re-splits `contacts + outsideContacts` at its ring (`TrafficMapGeometry.split`), and `TVRadarRootView` raises `model.queryRadiusFloor` when the map reaches past the radar's query. Its style is `wtf.mapType` (`standard` / `satellite` / `hybrid`; MapKit has no topographic style): imagery gets a lighter wash, a full-strength ring and dark-scheme labels. TV trails are `TrafficMapGeometry.shortTrailBands` (five minutes, fading out the whole way) at `TVMapLayout.trailWidth`, the standard map's rings are faded (`TVMapLayout.ringOpacity`), the paper wash is lighter (`TVMapLayout.washOpacity`, 0.35 vs 0.45; imagery 0.2 less) and the observer dot has no "You · place" label; iPad keeps the 15-minute `trailBands`. With the map on screen, holding ● on the hero (`onLongPressGesture`, 0.6 s) opens the map panel on the map's side (Range and Style chip columns, focus starts on the current range); a pick applies and returns focus to the hero, MENU closes it. Range and style are also in Settings → Display → Map. DEBUG `-wtf.debugMapPanel YES` opens the panel; `TVMapPanelUITests` drives it with the Siri Remote.

TV extras: the dock has a Logbook item (`TVLogbookView`: the same five tabs in the TV's top tab bar, pages in `UI/TV/TVLogbookTabs.swift`; Sightings is two columns, this week's days and older months on the left, that period's aircraft on the right; chart cards are focusable so the remote can scroll to them; a tab opens sightings, badges and airframes through `TVLogbookActions`), the detail screen toggles Nearby / Full Route, Radar settings include alerts (delivered as on-screen notices, and read aloud by `AlertSpeaker` when "Speak alerts" / `wtf.spokenAlerts` is on; sentences come from `SpokenTraffic` in `Radar/TrafficAlerts.swift`; while one is read out, `AlertSpeaker.speakingFlightID` pulses that aircraft purple, `Palette.announce`, on the radar edge and the map), "Alert ahead" (`wtf.overheadAlertLead`, seconds before closest approach, default 150) and the logbook switch. First run (or Settings → About → Take the tour) shows `TVOnboardingView` (`UI/TV/`), same pages and drawings with a Siri Remote page instead of Sky View; its last page goes to Settings → Location, demo traffic, or straight to the radar. `WhatTheFlightTopShelf/` is a Top Shelf extension (tvOS only) that fetches traffic around the shared observer and shows Planespotters photos; selecting an item opens `whattheflight://flight/<id>`.

### Apple Watch
`WhatTheFlightWatch/` is a standalone watchOS 11+ app (`WKRunsIndependentlyOfCompanionApp`, embedded in the iOS app via "Embed Watch Content" with an ios platform filter) that runs the same `RadarModel` with its own GPS (`WatchLocationService` in `WatchSensors.swift`; its `precision`, set by `WatchRootView`, is `radar` = a hundred-metre fix, `pointing` = ten metres while Identify or Find is open, `coarse` = three kilometres in iPhone's-spot mode, kept only for true north). `WristPointer` samples Core Motion at 30 Hz but publishes `pointing` only once it has moved `WristPointing.redrawDegrees`, so Identify and Find don't redraw per sample. Spec and decisions: `Apple Watch Spec.md` at the repo root; open items (performance, UI, options) in `Apple Watch Enhancements Spec.md`, same markers as `Enhancements Spec.md`.
- `WatchRootView` is three vertical pages (`TabView` `.verticalPage`): `WatchSettingsView` above (a "Nearby aircraft" row first), the radar, `WatchNearbyList` below. No banners on the Watch: alerts are haptics only.
- `WatchRadarView`: hero + perimeter on the Watch's rounded rectangle (`WatchRadarLayout`: max 8 icons, mile labels on the nearest 4 at 40–42 mm, corner obstacles for the clock and the pointer button). Swipe left / the Digital Crown step `focusNext`, swipe right `focusPrevious`; double tap (`handGestureShortcut` on the "Nearest" button) returns to the nearest; long press on the hero pins. The only toolbar button is the pointer: tap opens Identify, hold switches Point ↔ Aim with a haptic. Wrist down (scene `.inactive`, Always-On) stops polling and GPS and `RadarModel.advanceClock()` dead-reckons once a minute; the approach chip's glow and the focused blip's pulse stop too (`isLuminanceReduced`). When the feed goes quiet after the first load (`RadarModel.isStale`: a failed poll, or none for `staleAfter` = 75 s, with a grace after every `start()`), the approach chip becomes `WatchStaleChip` ("NO SIGNAL · 1:32", tap retries) and an empty radar shows No signal + Retry, never in Always-On. `WatchRootView` reads nothing that changes per tick: the centre state lives in `WatchRadarView` and the settings page's count in `WatchNearbyCount`, so only the radar redraws each second.
- First run shows `WatchTourView` (`WatchTour.swift`, `wtf.watch.hasSeenTour`, replay from Settings → Take the tour) before the location prompt: quick pages for swipes/taps, then the pointer button (a working copy: tap → its page, hold → switch style), Point and Aim acted out with the real haptics and the call-out, Find (real `AzimuthStrip` / `ElevationGauge`), and a style picker with "Try Identify". DEBUG: `-wtf.debugTourPage N`.
- `WatchFlightDetail` (Handoff `NSUserActivity` `SargeyWargey.WhatTheFlight.flight` → iPhone flight details), `WatchNearbyList`, `WatchSettingsView`.
- Two aim styles for Identify and Find (setting `wtf.watch.aimStyle`, Settings → Identify & Find → Aim with, or hold the radar's pointer button): **Point** (arm out, the forearm is the pointer) and **Aim** (hold the Watch as if reading it and sight along its top edge — `WristPointing.sightLine`; turn your body, tilt your wrist; the screen faces you so watchOS doesn't dim it). A red `AimMarker` sits on the aiming edge: top for Aim, the finger side for Point.
- Both modes use `PointingLayout` (`PointingUI.swift`). Aim is always upright. In Point the content auto-rotates like a phone: its top goes to whichever screen edge is highest (`WristPointing.screenTurn` from gravity, debounced in `WristPointer.screenTurn`), so palm-down it reads toward the hand and thumb-up it runs upright along the arm. The screen-vs-Core-Motion axis sign comes from the verified arm direction (`WristPointing.displaySign`), so it follows the wrist and crown settings. "Turn screen around" (`wtf.watch.flipScreen`) adds half a turn if it still reads upside down. Nav bar hidden; watchOS keeps its clock in the screen's top-right, so `PointingMetrics` puts the close button in the free top corner and insets the bottom row / gauge. The readout shows the Watch's wrist and crown settings. Sensors via `WristPointer` (Core Motion; compass + gravity fallback; "Reverse arm direction" = `wtf.watch.flipPointing`). Only the forearm axis counts, so wrist twist doesn't matter. While either mode is open the root view keeps the radar and GPS running when the screen dims.
  - **Identify** (`IdentifyView`, the radar's hand button, Siri "Identify a plane"): names what you point at. `WristPointing.candidates` = aircraft within 15 mi (`identifyRangeMiles`; the Watch sets `RadarModel.queryRadiusFloor` so the feed covers it) and ≥ 3° up (helicopters ≥ 1°, `WristPointing.isIdentifiable`), inside a 10° cone; `IdentifyTracker` needs a 0.5 s hold, then keeps the name within 15°. Before anything's in the cone, the lead (`WristPointing.lead`: nearest the arm on the compass within 30°, sticky by 4°) is highlighted on the strip and drawn as a dashed band on the `ElevationGauge` (`isPreview`) so you can set the height while still swinging round. The strip and gauge draw each aircraft's own silhouette (`AzimuthStrip.Mark(contact:)`; on the strip it faces its track with the arm's direction up). Tick on acquire, `.success` on naming, spoken call-out (`SpokenTraffic.identification`, `IdentifySpeaker`, setting `wtf.watch.speakIdentification`). Crown cycles aircraft in the cone; tap the card for details. Pointing arm-out, watchOS judges the wrist down (screen dimmed, scene inactive) while the sensors and feed keep running: `IdentifySpeaker.prepare()` sets up the audio session on open, while the app is still active (an inactive app can't start one), and the Watch app declares the `audio` background mode (`UIBackgroundModes` in `Config/WhatTheFlightWatch-Info.plist`, merged through `INFOPLIST_FILE` like the iOS `Config/WhatTheFlight-Info.plist`; not `WKBackgroundModes`, which only takes session types such as `workout-processing` and fails App Store upload with `audio`; the `INFOPLIST_KEY_` form isn't honoured for this key, and a plist inside the synchronized `WhatTheFlightWatch/` folder gets copied as a resource) so a sentence under way survives leaving the screen; the lock also goes out as `WristTapNotification` (`WatchNotification.swift`: category `wtf.traffic` so the long-look shows the aircraft, a `wristTap` userInfo marker the delegate lets through with sound, one identifier so taps replace each other, cleared when the screen closes, time-sensitive) because `WKInterfaceDevice.play` is only honoured for an active app; Find does the same on lock. The Watch asks notification permission the first time Identify or Find opens in Point. Both screens draw larger and drop the readout under `isLuminanceReduced`. How long the app stays up is the user's Return to Clock setting; the Identify & Find footer and the tour's Point page say so.

Timelines come from `NearbyTraffic.timeline` (`Services/SharedRadarStore.swift`, unit-tested): a `SkyMoment` a minute apart for five minutes plus one at each close pass and one as it clears, then "Open to refresh". ## Architecture

### Core Structure
- **MVVM Pattern**: Uses ViewModels (`MainViewModel`, `SettingsViewModel`) to manage state and business logic
- **Protocol-Oriented Services**: Service layer abstractions enable testability and dependency injection
- **Platform-Specific UI**: Conditional compilation for iOS/macOS differences using `#if os(macOS)`

### Key Components

#### Models (`WhatTheFlight/Models/`)
- `FlightData.swift`: Core flight data structures with nested types for airline, aircraft, route, and position
- `ConnectionStatus.swift`: Network connection state management
- `GeographicBounds.swift`: Coordinate boundary definitions for monitoring areas
- `NotificationSettings.swift`: User notification preferences
- `DisplayPreferences.swift`: UI customization settings

#### Services (`WhatTheFlight/Services/`)
- `FlightService.swift`: Primary service managing flight data fetching, monitoring, and state
- `NetworkManager.swift`: HTTP client for FlightRadar24 API interactions
- `LocationManager.swift`: Core Location wrapper for user position tracking
- `SettingsManager.swift`: UserDefaults persistence layer

#### ViewModels (`WhatTheFlight/ViewModels/`)
- `MainViewModel.swift`: Central state manager coordinating all services
- `SettingsViewModel.swift`: Settings UI state and persistence

#### Views (`WhatTheFlight/Views/`)
- `ContentView.swift`: Root view coordinator
- `FlightDisplayView.swift`: Primary flight information UI
- `SettingsView.swift`: Configuration interface
- `iOSComponents.swift` / `macOSComponents.swift`: Platform-specific UI components

### Testing Structure
- **Unit Tests**: Service and model testing with mocks in `WhatTheFlightTests/`
- **UI Tests**: Full application flow testing in `WhatTheFlightUITests/`
- **Mocks**: Comprehensive mock implementations for all service protocols

### Key Patterns
- **Service Protocols**: All services implement protocols for testability (`FlightServiceProtocol`, `NetworkManagerProtocol`)
- **ObservableObject**: ViewModels and services use Combine for reactive UI updates
- **Async/Await**: Modern concurrency throughout the networking layer
- **Platform Adaptation**: Conditional compilation and protocol-based platform differences

### FlightRadar24 API Integration
The app uses unofficial FlightRadar24 API endpoints with specific data parsing for the array-based response format. The `FlightService` handles rate limiting, retry logic with exponential backoff, and real-time monitoring with configurable intervals.
