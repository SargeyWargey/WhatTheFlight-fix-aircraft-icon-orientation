# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

WhatTheFlight is a SwiftUI-based flight tracking application that monitors aircraft overhead using FlightRadar24 API data. The project targets iOS, macOS, and visionOS platforms and displays real-time flight information within configurable geographic bounds.

## Build & Test Commands

This is an Xcode project using standard Xcode build commands:

- **Build**: `xcodebuild -project WhatTheFlight.xcodeproj -scheme WhatTheFlight -configuration Debug build`
- **Test**: `xcodebuild -project WhatTheFlight.xcodeproj -scheme WhatTheFlight -configuration Debug test`
- **Run Tests**: `xcodebuild test -project WhatTheFlight.xcodeproj -scheme WhatTheFlight -destination 'platform=iOS Simulator,name=iPhone 15'`
- **Clean**: `xcodebuild -project WhatTheFlight.xcodeproj -scheme WhatTheFlight clean`

For development, open `WhatTheFlight.xcodeproj` in Xcode.

## Release notes (TestFlight) — every session

Testers get a changelog with each TestFlight build. When a change is something a tester would notice (a new feature, a visible behaviour or design change, a bug fix), write a note for it before you finish: one file per change in `ReleaseNotes/unreleased/`, named `YYYY-MM-DD-short-slug.md`. Keep updating your own note as the change evolves, and never edit or delete another session's note (several sessions run at once in this folder). Skip refactors, tests, tooling, docs and DEBUG-only launch arguments. Format:

```markdown
---
kind: new                  # new | improved | fixed
platforms: iPhone, iPad    # any of iPhone, iPad, Apple TV, Apple Watch; or all
---
Sky View zooms to 5×: pinch, or tap the 0.5× / 1× / 2× / 5× chips.
Try: point at a distant aircraft and tap 5×.
```

Write for testers, not developers: what they'll see and where to find it, in a sentence or two, with no type or file names. The optional `Try:` line becomes a "What to Test" prompt. A Stop hook (`.claude/hooks/release-notes.sh`) reminds you once if you changed app code without writing a note; answer it with a note, or with one line saying why none is needed. When a build goes out, `/release-notes [build]` (`.claude/skills/release-notes/`) folds the notes into `CHANGELOG.md` and writes the TestFlight text.

## iOS / iPadOS app (radar v2) — start here

iOS runs the redesigned radar (`RadarRootView`) and tvOS `TVRadarRootView`, selected in `WhatTheFlightApp.swift`; watchOS is its own app. The Mac runs the iPad app ("Designed for iPad": the main and test targets list only iOS and tvOS in `SUPPORTED_PLATFORMS`, with `SUPPORTS_MAC_DESIGNED_FOR_IPHONE_IPAD = YES`); there `SkyViewSupport.isAvailable` (`UI/RadarScreen.swift`) is false, so Sky View's button, lift-to-look, Find in the Sky and `whattheflight://sky` are gone. The legacy `ContentView` stack described under "Architecture" below (`WhatTheFlight/Legacy/`, tests in `WhatTheFlightTests/Legacy/` and `WhatTheFlightUITests/Legacy/`, every file wrapped in `#if os(macOS) || os(visionOS)`, plus the macOS scene in `WhatTheFlightApp.swift` and the stray `WhatTheFlight/Views/tvOSComponents.swift`) is no longer compiled anywhere and is waiting to be deleted (Enhancements C11). Don't build on it.

Layout (all under `WhatTheFlight/WhatTheFlight/`):
- `Core/` — platform-neutral, unit-tested logic: `GeoMath` (distance, bearing, dead reckoning, closest approach, elevation above the horizon), `Flight` / `RadarContact` (`RadarContact.altitudeFeet` is dead-reckoned from the vertical rate like the position, capped at 90 s: show and say it rather than `flight.altitudeFeet`; `RadarContact.profile` is a `FlightProfile`: operator, notable tags, type, silhouette, airline, built once per flight per feed by `RadarModel`; per-tick code and views read it rather than the `Flight` computed properties), `Log` (one `os.Logger` per area: feed, logbook, sync, link, sensors, camera, alerts, ui; use it instead of `print`), `PollingPolicy` (the poll interval, which has no setting: 5 s within a mile of the nearest aircraft (now or within 90 s), then 5 s + 1 s per mile up to 25 s, 30 s when the feed reports nothing; Low Power Mode × 1.5 with a 10 s floor; `RadarModel.pollsFastest`, set by Sky View and the Watch's Identify / Find, holds it at the floor; Watch floor 10 s), `FlightFeedParser` (FR24 `feed.js` array format), `PerimeterTrack` (rounded-rect edge path + optimal icon spacing; its 1,440 samples are cached by rect, so layouts can rebuild it freely), `FocusPolicy` (which aircraft owns the centre), `OperatorInfo` (the line under the flight number: airline, "Private aircraft · 🇺🇸 United States", "Unlisted operator XYZ"), `NotableTraffic` (emergency squawks, military, government, air ambulance, rare types), `RouteProgress` (miles flown / to go), `SkyProjector` (pinhole camera maths for Sky View: project / unproject, `reframed` for a photo or video frame), `CameraZoom` (Sky View lens maths: field of view per zoom factor, 0.5× / 1× / 2× / 5× stops), `SkyCorrection` (Sky View visual lock-on: `SkyBlobDetector` finds the aircraft as a dot near its predicted spot, `VisualFix`, and the learned compass yaw applied to every label), `Whereabouts` ("Where is it now?" wording: in the air / on the ground at ATL, still on vs now flying, distance from you), `WristPointing` (Apple Watch Point & Find: forearm direction from attitude + wrist/crown settings, guidance, haptic cadence).
- `Data/` — offline catalogs: airlines (ICAO + radio callsign), aircraft types + helicopter detection + radar silhouettes (`AircraftTypeCatalog.silhouetteCodes` → `AircraftSilhouette`; unknown codes get the airliner), airports (IATA → city/name/coordinates), `RegistrationCountry` (tail-number prefix → country). `AirlineCatalog+Data.swift` (~5,800 rows, OpenFlights, ODbL) and `AirportCatalog+Data.swift` (~8,800 rows, OurAirports, public domain) are GENERATED by `Scripts/generate_catalogs.py`; the hand-curated lists in `AirlineCatalog.swift` / `AirportCatalog.swift` override them, so fix names there. `Catalogs.warmUp()` parses them off the main thread at launch (app inits, widget / complication / Top Shelf providers). Callsign lookup order: feed airline field → special words (`SAM`, `LIFE`, `NAVY`…) → 3-letter ICAO prefix followed by a digit.
- `Radar/RadarModel.swift` — `@Observable` state machine: polling with backoff, 1 Hz dead-reckoning tick, radius filter, focus, queued notices, per-flight trails (feed positions seen while watching, for the map). Trails are kept only out to 1.5× the radius (or the TV map's ring, `trailRadiusFloor`) plus focused and pinned aircraft. It also feeds `logbook?.record(...)` (`isLogging`: live traffic only — never demo, never an iPhone custom spot; the TV sets `logsCustomSpot` because its set place is its real location) and runs `TrafficAlertEngine`; alerts go to `onAlert` or become notices. The observer coordinate is pushed in, so it has no CoreLocation manager dependency.
- Pinning & worldwide search: one "pin" concept everywhere (hold the hero, TV ⏯ / dock, detail screens). The aircraft lists have no pin buttons on their rows: a row brings the aircraft to the radar, and a pinned aircraft that isn't flying (no details to unpin it from) is unpinned with a swipe on iPhone / iPad or a hold on the TV, where a click shows where it is now. Pins are `PinnedAircraft` (in `Core/FocusPolicy.swift`; matched by registration, else callsign, so they follow an airframe onto its next leg), stored in `RadarSettings.pinnedAircraft` (`wtf.pinnedAircraft`, JSON, max `RadarModel.maxPins` = 5; the oldest makes way with a notice). `RadarModel` looks up pins the main feed's box missed with `FlightFeed.lookup` every ~20 s (`pinnedFlights`, dead-reckoned between), so they appear in `outsideContacts` however far away; `pinnedOutside` / `perimeterContacts` put them on the radar edge, `pinnedIDs` feeds `PerimeterLayer` / `TrafficMap` (a pinned aircraft's mile label on the radar edge is yellow, `Palette.pinned`, the same yellow as the pin by the flight number on the hero; never faded; on the map a pinned aircraft's trail is yellow too, half again as wide, and that's its only mark there). `focus.isPinned` is always derived (every focus change goes through `setFocus`). `focus(on:)` pins an aircraft outside the radius (search, logbook "Show on Radar", detail screens, deep links, the TV's lists); map taps and radar-edge taps pass `pinning: false`, so an aircraft picked on the map outside the radius is only held (`RadarFocus.isHeld`): it keeps the centre and rides the radar edge while it's within the map's fringe (`RadarModel.fringeMiles`, 1.5× the radius), then the nearest takes over ("… flew out of range"); flying into the radius makes it an ordinary focus, pinning it drops the hold. `RadarModel.searchAnywhere` → `FlightRadarFeed.search(FlightSearchQuery)`: parallel world `feed.js` requests (`reg=`, `flight=`, `callsign=`; FR24 filters are uppercase prefix matches, take comma lists and AND together; registrations only match with their hyphen, so `RegistrationCountry.hyphenatedForms` adds `G-XLEI` for `GXLEI`), plus `airline=` (exact ICAO designators) and `airport=` (exact IATA codes, flights to and from) when the text names them: `FlightSearchQuery` (in `Services/FlightFeed.swift`, built off the main thread) reads airlines from names of 4+ letters (`AirlineCatalog.search(namesOnly:)`, "american" → AAL…) and airports from a 3-letter code or a city / name word (`AirportCatalog.search`, curated airports only when any match: "chicago" → ORD, MDW). Open data (`ReadsbFeed`) searches tail numbers and callsigns only. UI: iPhone `FlightSearchSheet`, TV `TVAircraftListView` (dock → Aircraft, now `.searchable`). The map follows a far-away pinned focus on its own (`TrafficMapGeometry.followsPinnedAlone`). Pins sync across iPhone, iPad, Apple TV and Apple Watch through iCloud key-value storage (`Services/PinSync.swift`, always on, independent of the logbook switch): one key per pin (`pin.<registration|callsign|flightID>`, JSON), `wtf.pinsInCloud` remembers which ids this device has seen in iCloud so a missing key means "unpinned elsewhere" vs "not sent yet"; demo pins never sync; `pinnedAt` orders pins and the cap across devices. All three apps' entitlements set `com.apple.developer.ubiquity-kvstore-identifier` to `$(TeamIdentifierPrefix)SargeyWargey.WhatTheFlight` so they share one store; `RadarModel.pinsDidChangeElsewhere` reacts to remote changes. DEBUG: `-wtf.debugPin <query>` pins the first worldwide hit, `-wtf.debugAircraftSearch <query>` pre-fills either search screen.
- Favourites: aircraft called out in yellow wherever they turn up, unlike pins never looked up worldwide or put on the radar edge from afar, and no cap but `RadarModel.maxFavorites` (500, for iCloud's 1,024 keys). `FavoriteAircraft` (in `Core/FocusPolicy.swift`, beside `PinnedAircraft`) is an airframe: matched by registration or ICAO hex, by callsign only when it has neither, so it's yellow on every leg; built from a `Flight` or a logbook `Sighting`. Stored in `RadarSettings.favoriteAircraft` (`wtf.favoriteAircraft`, JSON); `RadarSettings.favoriteSet` (`FavoriteSet`: `contains(flight / sighting / airframe:)`) is kept with it and reaches views as `\.favoriteAircraft` (declared in `UI/PerimeterLayer.swift`, set at each app's root and on their sheets / covers); screens without the model (logbook aircraft and sighting pages) add and remove through `\.toggleFavorite` (`FavoriteToggle`). Edit through `RadarModel.favorite` / `unfavorite` / `toggleFavorite` (the `FavoriteAircraft` overload matches the same airframe however it was saved); `state(of:)` says visible / on the ground / unseen. Shown: the whole icon yellow on the radar edge and the map (`AircraftBlip(isFavorite:)`: emergencies stay red, the focus keeps its red halo), a heart by the operator line on the hero (`FlightHero`) and the TV detail, `FavoriteTag` ("♥ FAVORITE") and a Favorite / Unfavorite button (`FavoriteButtonStyle`) on the iPhone / iPad details, a Favorite pill on the TV's, a Favorites section first in `FlightSearchSheet` / `TVAircraftListView` (live rows when flying nearby, otherwise tail number, type and Where Is It Now?; listed once, before pins; swipe any iPhone row to add or remove), and yellow names with a heart in the logbook (sighting rows, Most Seen via `LogbookRankRow(marksFavorites:)`, records, badge pages, the airframe and sighting pages, which also get `LogbookFavoriteButton`; the TV's rows, rankings and cards). The mark is a heart because the "rare" tag and "unlocked it" already use a star. Colours: `Palette.favorite` (the pin's yellow) for icons, `Palette.favoriteText` (deeper gold by day) for names. Synced like pins by `FavoriteSync` (`fav.<id>` keys, `wtf.favoritesInCloud`, demo favourites stay local); `Services/PinSync.swift` holds the shared `CloudListSync<Item: CloudListItem>` behind both, which counts an id as seen only once iCloud really holds it, so without iCloud (signed out, an unsigned build) nothing is mistaken for removed elsewhere. The iPhone / iPad details spell out the cities under the airport codes (`DetailRoute`; the hero's `RouteLine` keeps them small).
- `Radar/SpotPhoto.swift` — Sky View photos: `SpotPhoto` (the aircraft and its stats at the shutter, where it sits in the frame) rides on `Sighting.photos` (merged as a union minus `removedPhotoIDs`); `SpotPhotoStore` keeps the logbook's 1600 px HEIC copy per photo in Application Support/SpotPhotos. Photographing an aircraft outside the radius still logs it (`Logbook.addPhoto`). The full-resolution original goes to the camera roll (add-only, no album, flight in IPTC caption/keywords; setting `wtf.skySaveToPhotos`).
- `Radar/Logbook.swift` — sightings persisted as JSON in Application Support (a file that won't decode is set aside as `Logbook-unreadable-<time>.json`, never saved over), `LogbookStats`, `DailyRecap` ("Today's highlights": notable aircraft, first-of-type, new airlines). `Radar/LogbookDigest.swift`: `LogbookDigest`, everything the logbook screens show, built in one pass (today, records, `LogbookDay` / `LogbookMonth`, `LogbookRanking` lists of aircraft seen more than once / airlines / types / routes / airports / countries, places, the sky charts, streaks, the busiest hour, first-of-type ids) and `LogbookFilter` (quick filters and a ranked entry's sightings). Views read `Logbook.digest`, cached per change and per day; past `Logbook.backgroundDigestThreshold` (2,000) sightings a change rebuilds it off the main thread while screens keep the old one. Per-sighting calendar maths goes through `DayClock` (Calendar calls are slow over 10,000 sightings). `Radar/LogbookSky.swift`: the place-dependent charts (hour, weekday, heading rose, altitude) are a `LogbookSky`, built for everywhere (`digest.sky`) and for each `LogbookSpot` (`digest.spots`: sightings grouped by observer coordinate, ~7 mi grid squares busiest first joining the nearest spot within 15 mi, named after their most common `placeName`; sightings without a position join the spot with their place name). A chart only shows once `LogbookSky.minimum` (50) aircraft back it (`showsTimes` / `showsHeadings` / `showsAltitudes`), else a "filling in" progress bar (`LogbookSkyProgress`). Hours and weekdays use each sighting's own `timeZone` (recorded at logging; older ones borrow their spot's usual zone). The Stats tab (iPhone, iPad, TV) is two halves: "Your sky" (one spot, picked by `digest.sky(_:near:)`: where you are once its charts are ready, else the spot with the most sightings; a menu on iPhone / iPad, chips on the TV, plus "All places") and "Everywhere" (summary, activity, records, rankings, places). "Your sky" leads with the altitude-vs-speed scatter (`UI/AltitudeSpeedChart.swift`; data and picking maths in `Radar/AltitudeSpeed.swift`, unit-tested): `LogbookSky.altitudeSpeed` (not built on the Watch) holds an `AltitudeSpeedPoint` per sighting with a speed, coloured by `FlightKind` (first match of military, helicopter, general aviation, cargo, business jet, else airline, from the operator line, tags and the type's helicopter flag; the operator lists are plain arrays on the enum). It's one vectorized `PointPlot`, Equatable on `AltitudeSpeedSet.fingerprint`, with the ring and callout in an overlay that alone reads `AltitudeSpeedSelection`, so picking a dot never redraws the dots. iPhone / iPad: tap, drag sideways or press and drag (`ScatterPicking.nearest`, 24 pt; vertical swipes still scroll). Callout times are always US Central (`AltitudeSpeed.timeZone`). After the rose comes the route web (`UI/RouteWebChart.swift`; `Radar/RouteWeb.swift`, unit-tested): `LogbookSky.routeWeb`, a directed chord diagram of the 8 busiest route airports (`RouteWeb.layout` gives the ring's angles; ribbons coloured by origin, arrowheads at the destination), a panel of the picked airport's routes, and a link to `LogbookRoute.filter(.route / .airport)`. On the TV both are `TVExplorableCard`s (`UI/TV/TVExplorableCard.swift`): on the page only a card that lifts with focus while the arrows carry on between cards; select opens `TVChartExplorer` full screen, where the chart is the only focusable view so every arrow moves the pick (scatter: `ScatterPicking.step`, 45° cone widening to 80°; route web: `RouteWebCursor`, ◀ ▶ round the airports, ▼ ▲ through their routes); click opens the scatter's full card or the route web's flights (presented over the explorer, so back returns to it); back closes what's open, then returns to Stats. The rose, hours, weekdays and altitude bands drill in through a `LogbookSkySlice` (one petal or bar): `digest.sightings(in:spot:from:)` lists exactly the aircraft its bar counts (spot membership via `LogbookSpot.contains(_ sighting:)`, local time via `SkyClocks`, shared with `LogbookSky.init`; unit-tested) and `digest.summary(of:spot:from:)` gives a `LogbookSliceSummary` (share of the chart, rank, top airlines / types / routes, typical altitude, usual hour, main direction), shown by `LogbookSliceOverview` (full, or `compact` under a chart). `LogbookFilter.sky(slice, spot:)` is the route to the aircraft (`LogbookFilteredView` leads with the overview); it only matches through the digest, never `LogbookFilter.matches`. iPhone / iPad: tap a petal (`LogbookHeadingRose(picked:onPick:)`, others turn grey) or one of the top three; tap or drag along the hour / weekday bars (`LogbookBarPicking`: tap + the scatter's `SidewaysScrub` / `PressAndScrub`, not `chartXSelection`, which ignores taps), a `LogbookPickedColumn` and callout on the bar, the pick stays. TV: every Stats chart is a `TVExplorableCard` (and the Overview's 14 days); `UI/TV/TVSkyExplorers.swift` holds `TVSkySliceExplorer` (arrows step only to bars with aircraft, panel = the overview) and `TVActivityExplorer` (days / months, `LogbookActivityChart(picked:)`), and a click opens `TVSightingListView` (overview left, every aircraft right). `Radar/LogbookAchievements.swift`: `Achievement` badges, derived from the sightings every time (nothing stored), 46 in five `Achievement.Group`s (Milestones, Rare Birds, Moments, Collections, Sky View); most have `tiers` (Plane Spotter 100 / 1,000 / 10,000 / 100,000 / 1,000,000) with `level`, `target` = the next level, and top levels are meant to need calendar time, travel or luck, not just a radar left running (Busy Sky only counts aircraft within 5 mi, so the radius doesn't help). A badge whose levels aren't plain counts sets `tierLabels` ("45,000 ft", "¼ mi") and `progressLabel`; best-ever ones (High Flier, Speed Demon, Right Overhead, Long Haul, Far From Home) set `isRecord`, so the ring shows levels earned and they're never "next up". Show progress with `progressText` / `targetLabel`, not `progress` / `target`. A maxed levelled badge gets a filled disc and an outer ring (`AchievementBadge`). `Logbook.onBadgeUnlocked` (wired to a radar notice on iPhone and TV) fires for new badges and levels, checked at most every 20 s when new sightings arrive; levels already announced are kept in `wtf.announcedBadges` by what they take (`spotter@1000`, so a changed ladder never skips or repeats one), and the first check on an existing logbook only records a baseline. Fence Spotter looks up airports with `AirportCatalog.nearest` (grid-indexed by degree); Six Continents uses `Airport.continent`. `LogbookDigest`, `LogbookSky` and `LogbookAchievements` are in the Watch target's membership list. Each `Sighting` records `devices` (`LogDevice`) and `placeName` (reverse-geocoded by `Services/PlaceNamer`, set on `RadarModel.logPlaceName`). `Services/LogbookSync` merges logbooks across iPhone / iPad / Apple TV with CloudKit `CKSyncEngine` (container `iCloud.SargeyWargey.WhatTheFlight`, zone `Logbook`, one record per flight id holding the sighting as JSON; copies merge via `Sighting.merged(with:)`; each photo's image is its own `SpotPhoto` record "photo-<id>" with a CKAsset, and `LogbookSync.downloadPhoto` fetches one on demand). Setting `wtf.iCloudLogbook`. Custom spots and demo traffic are never logged on iPhone (`RadarModel.isLogging`); the radar shows a "Custom spot · … · not logged" tag along the bottom. Demo traffic turns the bar's aircraft count into a solid ink "DEMO n" lozenge (`StatusBadge(highlightsDemo:)`, the TV keeps the glass badge) and adds a "Demo traffic · simulated aircraft · not logged" tag (`DemoTrafficTag`; tap → "Switch to Live Traffic"). Both tags sit just above the bar. `Radar/TrafficAlerts.swift` — overhead (closest approach within N mi in ≤150 s) and notable alerts, once per flight per reason.

- `UI/` — SwiftUI views. ### Apple Watch
`WhatTheFlightWatch/` is a standalone watchOS 11+ app (`WKRunsIndependentlyOfCompanionApp`, embedded in the iOS app via "Embed Watch Content" with an ios platform filter) that runs the same `RadarModel` with its own GPS (`WatchLocationService` in `WatchSensors.swift`; its `precision`, set by `WatchRootView`, is `radar` = a hundred-metre fix, `pointing` = ten metres while Identify or Find is open, `coarse` = three kilometres in iPhone's-spot mode, kept only for true north). `WristPointer` samples Core Motion at 30 Hz but publishes `pointing` only once it has moved `WristPointing.redrawDegrees`, so Identify and Find don't redraw per sample. Spec and decisions: `Apple Watch Spec.md` at the repo root; open items (performance, UI, options) in `Apple Watch Enhancements Spec.md`, same markers as `Enhancements Spec.md`.
- `WatchRootView` is three vertical pages (`TabView` `.verticalPage`): `WatchSettingsView` above (a "Nearby aircraft" row first), the radar, `WatchNearbyList` below. No banners on the Watch: alerts are haptics only.

The only toolbar button is the pointer: tap opens Identify, hold switches Point ↔ Aim with a haptic. When the feed goes quiet after the first load (`RadarModel.isStale`: a failed poll, or none for `staleAfter` = 75 s, with a grace after every `start()`), the approach chip becomes `WatchStaleChip` ("NO SIGNAL · 1:32", tap retries) and an empty radar shows No signal + Retry, never in Always-On. `WatchRootView` reads nothing that changes per tick: the centre state lives in `WatchRadarView` and the settings page's count in `WatchNearbyCount`, so only the radar redraws each second.

## Architecture

### Core Structure
- **MVVM Pattern**: Uses ViewModels (`MainViewModel`, `SettingsViewModel`) to manage state and business logic
- **Protocol-Oriented Services**: Service layer abstractions enable testability and dependency injection
- **Platform-Specific UI**: Conditional compilation for iOS/macOS differences using `#if os(macOS)`

### Key Components

#### Models (`WhatTheFlight/Models/`)
- `FlightData.swift`: Core flight data structures with nested types for airline, aircraft, route, and position
- `ConnectionStatus.swift`: Network connection state management
- `GeographicBounds.swift`: Coordinate boundary definitions for monitoring areas
- `NotificationSettings.swift`: User notification preferences
- `DisplayPreferences.swift`: UI customization settings

#### Services (`WhatTheFlight/Services/`)
- `FlightService.swift`: Primary service managing flight data fetching, monitoring, and state
- `NetworkManager.swift`: HTTP client for FlightRadar24 API interactions
- `LocationManager.swift`: Core Location wrapper for user position tracking
- `SettingsManager.swift`: UserDefaults persistence layer

#### ViewModels (`WhatTheFlight/ViewModels/`)
- `MainViewModel.swift`: Central state manager coordinating all services
- `SettingsViewModel.swift`: Settings UI state and persistence

#### Views (`WhatTheFlight/Views/`)
- `ContentView.swift`: Root view coordinator
- `FlightDisplayView.swift`: Primary flight information UI
- `SettingsView.swift`: Configuration interface
- `iOSComponents.swift` / `macOSComponents.swift`: Platform-specific UI components

### Testing Structure
- **Unit Tests**: Service and model testing with mocks in `WhatTheFlightTests/`
- **UI Tests**: Full application flow testing in `WhatTheFlightUITests/`
- **Mocks**: Comprehensive mock implementations for all service protocols

### Key Patterns
- **Service Protocols**: All services implement protocols for testability (`FlightServiceProtocol`, `NetworkManagerProtocol`)
- **ObservableObject**: ViewModels and services use Combine for reactive UI updates
- **Async/Await**: Modern concurrency throughout the networking layer
- **Platform Adaptation**: Conditional compilation and protocol-based platform differences

### FlightRadar24 API Integration
The app uses unofficial FlightRadar24 API endpoints with specific data parsing for the array-based response format. The `FlightService` handles rate limiting, retry logic with exponential backoff, and real-time monitoring with configurable intervals.
